# 出去走走 · 小走 V3

「出去走走」的 V3 可运行版本，以真实场地和接待人物为核心，包含完整前端、账号体系、SQLite 数据库、预约流转、小走文字模型问答、分层记忆、会话摘要和豆包实时语音代理。文字与语音共用同一份用户上下文和提示词，明确事实仍由确定性规则兜底。

线上地址：<https://beyondyouth.com.cn/>

本仓库同时保留两套实现：

- `xiaozou-v3/`：当前线上运行的 V3 版本，也是本文档的主要说明对象。
- `src/`：早期 Next.js 2.0 原型，保留用于查看旧设计，不是当前线上服务。

---

## 1. 产品目标

小走不是简单的活动搜索框，也不是代替用户做决定的“导购”。它需要在合适的时候知道：

1. 正在说话的是谁；
2. 这个用户已经确认或取消了哪些行程；
3. 用户明确留下过哪些稳定偏好；
4. 最近聊过什么；
5. 平台上有哪些真实场地和接待人物；
6. 哪些问题资料不足，不能直接编造答案。

因此 V3 的实现重点不是增加聊天特效，而是建立一套统一、可更新、可纠正、按账号隔离的数据和上下文体系。

### 当前主要能力

- 家门口、远方、发现、场地详情、个人中心等完整移动端页面。
- 注册、登录、退出、账号切换和云端状态同步。
- 用户基础资料：常居城市、出行节奏、同行方式、兴趣和补充说明。
- 预约、主理人确认、用户取消和重新预约。
- 小走文字模型问答、确定性事实问答与最多两个真实场地推荐。
- 当前状态、稳定偏好、预约草稿、行后反馈和弱行为信号分层保存。
- 用户记忆的新增、选择性写入、槽位替换、纠正、编辑和删除。
- 文字、语音、按钮、预约沟通和反馈等交互的会话记录与近期摘要。
- 结合行程、最近话题、本次选择和偏好轮换的文字/语音开场。
- 服务端统一生成文字与语音的人设、记忆和用户上下文。
- 真实 PCM 音频流接收、顺序播放和资源释放。
- 场地、人物目录的数据库存储和版本化更新。

## 2. 技术方案

### 2.1 技术选型

| 层级 | 实现 |
|---|---|
| 前端 | 单个 `index.html`，原生 HTML/CSS/JavaScript，无前端框架依赖 |
| 服务端 | Node.js 原生 `http` / `https` / `tls` |
| 数据库 | SQLite，使用 Node.js 内置 `node:sqlite` |
| 会话 | HttpOnly Cookie，数据库只保存会话 Token 的 SHA-256 哈希 |
| 密码 | 每个用户独立 Salt，`scrypt` 哈希 |
| 语音 | 同源 HTTP 票据代理 + 同源 WebSocket 代理 + 豆包实时语音 |
| 部署 | Docker Compose、Node 23、Caddy 自动 HTTPS |
| 图片 | V3 原型图片部署于 `images/`，补充素材位于 `assets/`，不依赖第三方占位图 |

V3 服务端没有第三方 npm 运行依赖。`package.json` 中的 `devDependencies` 为空。

### 2.2 目录结构

```text
xiaozou-v3/
├── index.html              # 全部移动端页面、交互、文字对话和语音播放
├── voice-proxy-server.js    # HTTP 服务、账号 API、语音 HTTP/WebSocket 代理
├── xiaozou-service.js       # 目录、档案、行程、记忆、摘要和统一小走上下文
├── catalog-seed.json        # V3 十个场地及人物的初始化种子
├── images/                 # V3 原型场地、人物、详情和分享封面原图
├── assets/                 # 其他补充图片资源
├── deploy/
│   └── Caddyfile            # HTTPS 和反向代理配置
├── docker-compose.yml       # Node + Caddy 容器编排
└── package.json             # 启动命令和 Node 版本要求
```

数据库文件、账号密码、会话 Cookie 和线上管理凭据不进入 Git 仓库。

仓库根目录的 `backups/xiaozou-memory-unified-20261106/` 保存当前“记忆统一版”的核心源码、完整提示词和恢复说明；它不参与线上运行，线上代码仍只读取 `xiaozou-v3/`。

## 5. 数据库设计

### 5.1 账号与同步

| 表 | 用途 | 关键约束 |
|---|---|---|
| `users` | 用户账号和显示名 | `username` 唯一 |
| `sessions` | 登录会话 | Token 哈希为主键，带过期时间 |
| `user_state` | 完整前端状态快照 | 每个用户一行，带 `revision` |
| `user_profiles` | 结构化基础资料 | 每个用户一行 |

`user_state` 保存预约、对话界面、角色、动态等状态。它是客户端状态快照，不是小走判断行程的唯一依据。

### 5.2 场地目录

| 表 | 用途 |
|---|---|
| `catalog_venues` | 场地完整 JSON、分类、顺序和更新时间 |
| `catalog_people` | 人物及其所属场地，人物与场地一对一关联 |
| `catalog_meta` | 目录版本等元数据 |

目录首次启动时从 `catalog-seed.json` 初始化。**后续修改种子文件不会覆盖已经存在的数据库目录**；已有环境需要通过管理员目录 API 更新。

### 5.3 行程投影

| 表 | 用途 |
|---|---|
| `itineraries` | 从最新状态快照投影出的独立行程记录 |

每次 `PUT /api/state` 在同一个事务里：

1. 更新 `user_state`；
2. 删除该用户旧的行程投影；
3. 按最新 `state.bookings` 重建投影；
4. 增加状态版本；
5. 一起提交或一起回滚。

这样既能保留完整前端状态，又能让服务端按状态查询行程。

### 5.4 会话与记忆

| 表 | 用途 |
|---|---|
| `conversation_turns` | 当前账号的文字/语音用户消息与小走回复 |
| `conversation_summaries` | 由近期会话生成的滚动摘要 |
| `memories` | 当前状态、稳定偏好、档案和行后反馈等分层记忆 |
| `opening_state` | 每个账号的开场轮换序号，避免每次固定同一句话 |

`memories` 同时保存 `status`、`updated_at` 和 `metadata.slot`，用于状态纠正、槽位替换和审计。旧的原始日志可以继续保留在数据库中，但不会被默认视为长期偏好注入文字或语音。

## 6. 行程状态：小走以什么为准

小走判断“现在有哪些行程”时，只把 `itineraries.status === 'accepted'` 的记录当作已确认行程。

| 状态 | 含义 | 是否算已约成 |
|---|---|---|
| `pending_host` | 已发出申请，等待主理人确认 | 否，单独说明 |
| `accepted` | 主理人已经确认 | 是 |
| `cancelled` | 用户已取消 | 否，仅回答取消记录时说明 |

重要边界：

- “我想去”只是一段聊天，不会直接生成已确认行程。
- 取消后记录仍可查询，但不会出现在当前行程中。
- 一个账号的预约不会出现在另一个账号的上下文里。
- 访客不能读取任何账号行程。

## 7. 小走文字问答逻辑

入口：`POST /api/chat`。

### 7.1 输入

```json
{
  "message": "叶万红是谁？",
  "session": {
    "mood": "想放空",
    "door": "家门口",
    "pace": "慢一点",
    "vibe": "少说话",
    "bias": "near",
    "shift": 0
  }
}
```

`session` 只保留以上白名单字段，避免把整段客户端状态或伪造系统提示带入服务端。

### 7.2 回答顺序

当前文字问答由上游文本模型与确定性规则共同完成，并与语音共用 `buildContext()`：

1. 场地人物、用户身份、真实行程、稳定偏好和平台目录等明确事实查询，使用确定性规则回答；
2. 状态、情绪、关系场景和其他一般对话，把当前消息及统一上下文交给上游文本模型理解；
3. 模型回答中出现的真实场地名称会映射为最多两个推荐 ID，其他内容不会生成虚假卡片；
4. 上游不可用或超时时自动回退到确定性规则，响应以 `understanding = model/rules` 标识实际链路；
5. 用户与助手回合仍由本系统入库，偏好捕获和账号隔离不因使用模型而改变。

目录中没有的信息不应被补写成事实。文字和语音都被明确要求不得虚构价格、地址、时间或人物经历。

### 7.3 文本模型与降级边界

一般对话由服务端请求 `https://ceo.pianai.love/api/chat`，请求只包含当前用户消息、服务端生成的 `systemPrompt` 和 `stream: false`。浏览器不能直接替换系统提示词，也不能通过请求体指定其他用户身份。

- 请求超时为 30 秒，响应上限为 1 MiB，回复最多保留 4000 个字符。
- 身份、真实行程、记忆核对、明确场地人物和平台目录查询优先走规则，避免模型编造事实。
- 模型不可用、超时、非 200 或返回空内容时，服务端记录警告并回退规则，不向用户暴露上游错误细节。
- `understanding` 只表示本次实际回答链路，不代表文字和语音使用同一个上游引擎；两者统一的是记忆、上下文和表达原则。

### 7.4 推荐

推荐只返回数据库中的场地 ID，前端再映射成对应卡片：

- 偏向家门口：从附近场地中选择；
- 明确想运动、徒步或溯溪：优先相关场地；
- 选择远方：从远方场地中选择；
- 想安静、慢下来：优先适合放空的场地；
- 换一组：通过 `shift` 轮换，但仍最多返回两个。

## 8. 记忆系统：完整实现说明

记忆系统分为六层，不能把它们混为一谈。

### 8.1 六层信息

| 层 | 保存位置 | 生命周期 | 是否进入长期记忆 |
|---|---|---|---|
| 本次会话状态 | 浏览器 `xiaoChat` | 当前选择、当前对话 | 否 |
| 用户基础资料 | `user_profiles` | 用户主动修改前持续存在 | 作为独立档案读取 |
| 原始会话记录 | `conversation_turns` | 持续保存 | 否 |
| 近期会话摘要 | `conversation_summaries` | 随新会话滚动更新 | 作为摘要读取，不等同偏好 |
| 长期记忆 | `memories` | 用户纠正或删除前持续存在 | 是，按过滤规则读取 |
| 行程状态 | `itineraries` | 随最新预约状态更新 | 作为事实读取，不写入偏好 |

### 8.2 记忆类型与交互采集

`memories.kind` 用来区分不同语义，不能把一次点击或一次心情都当成稳定人格：

| 类型 | 含义 | 典型来源 |
|---|---|---|
| `preference` | 稳定喜欢、不喜欢和边界 | 明确的文字表达、用户主动保存 |
| `profile` | 可长期使用的用户资料 | 档案或明确资料记忆 |
| `journey` | 本次心情、人数、节奏等当前状态 | 小走按钮、当前出行选择 |
| `feedback` | 某次真实行程后的体验 | 行后反馈 |

稳定表达包括“我喜欢安静”“我不喜欢拍照”“别催我”等。`preference` 通过 `metadata.slot = preferences/boundaries` 区分喜欢与边界；按钮状态使用 `journey` 和 `metadata.slot = current.<field>`；行后反馈使用 `feedback` 和 `metadata.slot = trip.<bookingId>.feedback`。

除文字输入外，以下来源也会进入 `conversation_turns`，供后续上下文使用：

- 小走心情、节奏、距离和偏好按钮；
- 主理人选择、预约沟通、人数和自由输入；
- 动态、评论等用户可见操作；
- 行后反馈与小走可见的按钮流程回复；
- 文字和语音最终 ASR、完整助手回复；
- 文字和语音开场。

“写入会话”不等于“写入长期记忆”。普通按钮和闲聊只作为当前上下文；只有明确偏好或业务上有明确用途的记录才进入 `memories`。所有登录用户记忆写入都必须以服务端当前账号为准。

### 8.3 什么不会写入长期记忆

- 普通闲聊；
- 一次性的“今天想去哪里”；
- 小走或语音模型自己的回答；
- 其他用户的资料；
- 访客对话；
- 预约的已取消状态；
- 未明确表达的情绪推测。

语音 ASR 和小走回复写入的是 `conversation_turns`，不是 `memories`。

### 8.4 偏好纠正

例如用户先说“喜欢安静”，之后说“喜欢热闹”：

1. 两条记录使用相同的 `kind` 和 `metadata.slot`；
2. 新记录写入前，旧记录被设为 `superseded`；
3. 默认查询只返回 `active` 记录；
4. 小走之后只读取“喜欢热闹”；
5. 操作在事务内完成，避免两条冲突偏好同时生效。

`profile`、`journey` 和 `feedback` 也使用同样的槽位替换机制。例如同一个 `current.mood` 只保留最新有效状态，不同预约的反馈则因 `trip.<bookingId>.feedback` 不同而分别保留。历史记录被标记为 `superseded`，不会被默认注入后续上下文。

### 8.5 编辑和删除

个人中心提供：

- 查看当前有效记忆；
- 修改内容；
- 删除不再需要的记忆。

行为说明：

- 修改时会校验该记忆属于当前账号；
- 修改后重新设为 `active` 并更新时间；
- 删除为数据库删除，不再进入任何后续上下文；
- 跨账号修改或删除返回 `404`，不泄露记录是否属于别人。

### 8.6 长期记忆的读取

构建上下文时：

1. 只查询当前 `user_id`；
2. 只取 `active` 记录；
3. 排除旧版本遗留的 `chat`、`voice_user`、`voice_assistant` 原始日志；
4. 最多注入最近 20 条；
5. 作为不可信用户数据放入上下文，而不是系统指令。

个人中心的“小走记忆”可以管理有效记录；原始会话仍留在会话表中，用于摘要，不会冒充稳定偏好。

### 8.7 会话摘要

每次写入会话记录后，服务端重新生成滚动摘要：

- 取最近 8 条用户/小走消息；
- 每条最多保留 180 个字符；
- 整体最多保留约 3000 个字符；
- 记录“用户：”和“小走：”角色；
- 更新当前账号唯一的一行摘要。

构建新上下文时，还会读取最近 6 条原始消息，并附加该摘要。

这是确定性的滚动文本摘要，不是语义向量检索，也不会把摘要中的每句话提升为长期偏好。

### 8.8 账号切换和访客

- 所有账号数据查询都以服务端 Cookie 解析出的 `user.id` 为条件。
- 浏览器上传的 `userId` 不会被用来选择语音用户上下文。
- 账号切换后重新从 `/api/state` 加载档案、状态、记忆和行程。
- 访客只携带本次会话白名单状态，不读取账号档案、行程、摘要或记忆。

## 9. 统一小走上下文

`buildContext()` 是小走上下文唯一构建入口。

### 9.1 注册用户

上下文依次包含：

1. 小走的角色、表达边界和真实性要求；
2. 当前用户基础资料；
3. 已确认行程；
4. 待主理人确认的申请；
5. 尚未约成的预约沟通草稿，包括人数、状态、节奏和期待；
6. 行后反馈与回忆；
7. 当前喜欢的主理人，明确标为弱信号而非稳定偏好；
8. 当前有效的分层记忆；
9. 近期会话摘要与最近 6 条原始对话；
10. 本次会话白名单状态；
11. 平台场地与人物的紧凑目录。

### 9.2 访客

访客上下文只包含：

1. 相同的小走角色和边界；
2. “当前为访客”的明确说明；
3. 本次会话状态；
4. 平台公开目录。

### 9.3 安全边界

上下文中的用户资料、记忆和对话都被视为**不可信数据**。即使用户文本里出现“忽略之前规则”，也不应被当作新的系统指令。

## 10. 语音实现

### 10.1 票据

浏览器请求语音票据时只发送：

```json
{
  "session": {
    "mood": "想放空",
    "door": "家门口",
    "pace": "慢一点",
    "vibe": "少说话",
    "bias": "near",
    "shift": 0
  }
}
```

服务端重新生成以下字段：

- `userId`
- `ceoId`
- `ceoName`
- `systemPrompt`
- `voiceId`
- `openingText`

客户端提交的伪造身份、人设或音色不会被采用。

文字开场通过 `POST /api/chat/opening` 获取，语音开场在票据生成时由同一个 `opening()` 产生。开场按已确认行程、待确认申请、本次选择、近期话题、稳定偏好和通用场景选择候选，并通过 `opening_state` 轮换，不再固定询问“今天想怎么走”。开场只引用已有信息，不把待确认申请说成已约成。

### 10.2 WebSocket 与 PCM

- 语音 WebSocket 与页面同源，避免跨域和 Cookie 混乱。
- 代理只删除 Origin、Referer、Cookie、Authorization 等不应转发的头。
- 浏览器通过 `ScriptProcessorNode` 获取麦克风数据，重采样为 16 kHz、单声道、16-bit PCM 后发送。
- 返回的二进制音频进入播放队列，并按 24 kHz PCM 解码播放。
- 每段音频按递增时间调度，避免多段同时播放或相互覆盖。
- 停止语音时关闭 WebSocket、麦克风流和音频上下文，并清理播放队列。

### 10.3 流式文本聚合

语音服务会把同一句话拆成许多 `chat` 分片，分片可能只有一个字，也可能在文本尚未结束时插入 `tts_start`。因此客户端不能把每个分片当作一条新消息，也不能把每次 `tts_start` 都当作回答结束。

`voiceState` 使用两个字段聚合当前回答：

| 字段 | 用途 |
|---|---|
| `replyText` | 当前回答所有 `chat.text` 的完整拼接结果 |
| `replyIndex` | 当前回答在 `xiaoChat.voiceReplies` 中的稳定索引 |

处理流程：

1. 第一个 `chat` 分片创建一个语音回复气泡，并保存其索引；
2. 后续分片只更新同一项 `voiceReplies` 和同一个 DOM 节点，不重新生成整段聊天；
3. `tts_start` 只清理上一段音频播放，不拆分文本回答；
4. 新 ASR 到达、用户停止语音或 WebSocket 关闭时，调用 `finishVoiceReply()` 结束当前回答；
5. `finishVoiceReply()` 清空聚合状态，重复调用不会重复保存；
6. 下一轮回答获得新的索引和气泡，不与上一轮混合。

### 10.4 ASR 与会话保存

ASR 的临时结果是不断覆盖的识别文本，不是多条用户发言：

- `is_final === false`：只更新输入框和语音状态，不写数据库；
- `is_final === true`：保存一条最终用户消息；
- `chat` 分片阶段：不保存助手消息；
- 回答结束时：保存一条拼接完整的助手消息。

访客不会写入账号会话。登录用户的文字和语音记录都进入 `conversation_turns`，但不会仅因收到语音分片就写入长期记忆。

## 11. API 一览

### 公开或访客可用

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/auth/me` | 当前登录状态 |

| POST | `/api/chat` | 小走文字模型/规则问答；登录后增加账号上下文 |

### 需要登录

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/state` | 状态、档案、记忆、行程 |
| PUT | `/api/state` | 保存状态并同步行程投影 |
| GET | `/api/profile` | 获取基础资料 |
| PUT | `/api/profile` | 更新基础资料 |
| GET | `/api/itineraries` | 获取行程投影 |
| GET | `/api/memory` | 获取有效记忆 |
| POST | `/api/memory` | 新增或替换长期记忆 |
| PUT | `/api/memory/:id` | 编辑当前账号的记忆 |
| DELETE | `/api/memory/:id` | 删除当前账号的记忆 |

### 目录管理员

| 方法 | 路径 | 说明 |
|---|---|---|
| PUT | `/api/catalog` | 全量更新目录，需当前版本号和管理员账号 |

目录管理员通过环境变量配置：

```bash
CATALOG_ADMIN_USERS=admin-a,admin-b
```

更新时携带当前 `version`。版本不一致返回 `409`，防止两个人同时编辑时互相覆盖。

## 14. 图片资源与本次修复

线上图片问题经历了两类不同原因：早期是服务器缺少资源导致破图；后续则是把 V3 原型 `images/` 错误替换为通用 `assets/` 素材，图片虽然能够加载，但内容与场地、人物不对应。动态目录加载还会用数据库中的错误路径覆盖页面静态数据。

本次修复方式：

- 将完整 V3 原型 `images/` 目录纳入仓库并部署到生产环境；
- 按原型逐项恢复 10 个场地的列表图、人物头像、详情主图和分享封面；
- 同步修正初始静态数据、`catalog-seed.json` 和已存在的生产数据库目录；
- 移除运行时将原型图片强制覆盖为通用素材的逻辑；
- 保留确有用途的 `assets/` 补充素材，不使用空白图、占位图或隐藏图片掩盖问题。

验证不能止于 HTTP 成功或 `naturalWidth > 0`。还需检查实际 DOM 图片路径与原型映射一致，并核对图片内容与场地、人物相符。验证范围包括首页、附近、远方、发现、小走推荐卡片、10 个场地详情及对应分享封面。

## 16. 当前边界

- 文字一般对话已经接入文本模型，明确事实仍走规则；文字与语音不是同一个上游引擎。
- 会话摘要是滚动文本摘要，不是向量数据库或语义检索系统。
- 记忆只处理明确偏好、当前状态、档案和真实反馈，不做隐式人格推断。
- 部分按钮和会话写入是异步请求，极端情况下仍可能失败、乱序或需要重试。
- 删除动态、评论与历史会话/记忆的联动尚不完整。
- 语音开场在票据生成时记录，不代表上游一定播放成功。
- 场地目录全量更新适合当前 10 个场地的规模；更复杂的运营后台可在后续单独建设。
- 当前账号和目录管理能力面向可运行产品验证，不等同于完整企业后台。
